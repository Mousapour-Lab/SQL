# Walkthrough

This document explains every script in the project in plain language: what it does, why it is written that way, and which Oracle concepts it uses. The goal is that you can open any line of this repository in an interview and explain it.

Read it in the same order the scripts run.

---

## 1. `schema/00_drop_all.sql`

**What it does:** removes every object the project creates (2 views, 1 package, 5 tables), so you can run the whole set of scripts again from an empty schema.

**Why it is written this way**

- `DROP TABLE` fails with **ORA-00942** when the table does not exist yet, which is exactly the case on a first run. Each drop is wrapped in a small PL/SQL block that ignores only that one error and **re-raises everything else**. So a first run is quiet, and a real problem (for example "table is locked") still shows up.
- The order is child-first: `stock_movements` and `purchase_order_lines` point at `items` and `purchase_orders`, so they must go first. A parent table cannot be dropped while a foreign key still references it.
- Dropping a table also drops the triggers on it, which is why there is no separate `DROP TRIGGER`.
- `PURGE` skips the recycle bin. Without it, dropped tables stay in the recycle bin and the names can collide on a re-run.

**Oracle concepts:** DDL, dependent objects and drop order, `SQLCODE`, the `EXCEPTION` section, `WHEN OTHERS` used together with `RAISE` (never on its own), `EXECUTE IMMEDIATE` for DDL inside PL/SQL.

## 2. `schema/01_create_tables.sql`

**What it does:** creates the five tables and all their rules.

**Why it is written this way**

- **Identity columns** (`NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`) let Oracle fill the primary key. `BY DEFAULT` means "generate a value if I do not supply one"; that is why the seed file can insert its own ids.
- **`NOT NULL`** marks what a row cannot live without: an item must have a sku, a name and a price.
- **Foreign keys** put the relationships in the database, not only in the application: an item cannot point to a supplier that does not exist.
- **`CHECK` constraints** hold the business rules that are true for every row: stock is never negative (`quantity_on_hand >= 0`), a movement is always positive and its direction is `IN` or `OUT`, a PO status is one of four values.
- `items.supplier_id` is nullable on purpose: a new item may exist before we pick a supplier.
- `purchase_order_lines.unit_price` is copied from the item instead of being looked up later, because the price at the moment of ordering is history and must not change when the item price changes.
- `UNIQUE (po_id, item_id)` stops the same item appearing twice in one PO, which would make receiving ambiguous.

**Oracle concepts:** data types (`NUMBER(10,2)`, `VARCHAR2`, `DATE`, `CHAR(1)`), identity columns, primary keys, foreign keys, `NOT NULL`, `CHECK`, `DEFAULT`, `UNIQUE`.

## 3. `schema/02_seed_data.sql`

**What it does:** inserts 5 suppliers, 15 items, 6 purchase orders, 15 order lines and 37 stock movements, then commits and fixes the identity sequences.

**Why it is written this way**

- Ids are typed by hand for suppliers, items, POs and lines, because the child rows have to point at them (`po_id = 3`). `stock_movements` has no hand-typed ids, because nothing references a movement.
- The movements use `INSERT ... SELECT ... FROM dual UNION ALL`, which is the normal Oracle way to insert many rows in one statement. A plain `INSERT ... VALUES` inserts one row only; Oracle has no multi-row `VALUES`.
- `quantity_on_hand` in `items` is **exactly** the net result of the movements below (total IN minus total OUT, per item). That is not decoration: the whole domain says "stock is the sum of the movements", so the sample data has to obey it. If you run a query that sums the movements per item, you get the number stored in `items`.
- The script commits at the end, and only once. A single commit at the end of a load script is easier to reason about than one commit per row.
- The last four `ALTER TABLE ... MODIFY (... START WITH LIMIT VALUE)` lines fix a real problem: hand-typed ids do **not** advance the identity sequence, so the next generated id would be 1 and collide. `START WITH LIMIT VALUE` moves the sequence to the highest id in the column plus one.
- `updated_at` is NULL for two items and one movement has no `reason`: nullable columns need at least one example, otherwise `NULL` handling is never exercised.

**Data to know for the tests:** item 1 has 22 in stock, item 6 has 24, item 11 has 45, item 15 has 0, and PO 3 is the only `ORDERED` order with lines.

**Oracle concepts:** `INSERT ... VALUES`, `INSERT ... SELECT`, `UNION ALL`, `dual`, `DATE 'YYYY-MM-DD'` literals, `COMMIT`, identity sequences vs. explicit ids.

## 4. `plsql/01_inventory_pkg.sql`

**What it does:** one package, `inventory_pkg`, with the three operations the application needs.

**Why it is written this way**

- **Package spec vs. body.** The spec is the public contract: parameter names, types and the exception. The body has the logic. Changing the body does not break the callers as long as the spec stays the same. A package also keeps related procedures together and lets them share the exception, which plain procedures cannot do.
- **`%TYPE`** (`purchase_orders.po_id%TYPE`) makes a parameter follow the column type. If the column ever changes, the package follows without edits.
- **`FOR UPDATE`** locks the row that is about to change. In `issue_stock` it stops two sessions from both reading "9 in stock" and both taking 9. In `receive_po` it stops the same PO being received twice at the same time.
- **`receive_po` in steps:** lock the PO → check the status is `ORDERED` → insert one IN movement per line → make sure something was inserted → set the status to `RECEIVED`. Each step is a plain statement, and the status changes last, so a failure in the middle leaves the PO unreceived.
- **`SQL%ROWCOUNT`** after the insert tells us how many lines were written. Zero means the PO has no lines, and marking it received would be a lie, so it raises an error.
- **The exception is named and numbered.** `e_insufficient_stock` is declared in the spec and bound to `-20001` with `PRAGMA EXCEPTION_INIT`. The package raises it with `RAISE_APPLICATION_ERROR(-20001, message)` so the caller gets both a message and a catchable name. That is why callers can write `WHEN inventory_pkg.e_insufficient_stock THEN ...` instead of matching on text.
- **No `WHEN OTHERS` inside the package.** Only `NO_DATA_FOUND` is handled, because "the id you gave me does not exist" is the one error we can translate into a useful message. Anything else is a real bug and must reach the caller unchanged.
- **No `COMMIT` anywhere.** The package does one unit of work and leaves the transaction open, so the caller can combine it with other work and commit or roll back once. Committing inside a reusable procedure makes transactions impossible to control.
- **`get_stock` returns NULL** for an unknown item, which is easier to use than an exception and is documented in the spec comment.

**Oracle concepts:** package spec and body, `CREATE OR REPLACE`, `IN` parameters and defaults, `%TYPE`, `SELECT ... INTO`, `FOR UPDATE`, `RAISE_APPLICATION_ERROR`, user-defined exceptions, `PRAGMA EXCEPTION_INIT`, `SQL%ROWCOUNT`, transaction control.

## 5. `plsql/02_triggers.sql`

**What it does:** keeps `items.quantity_on_hand` and `items.updated_at` correct automatically.

**Why it is written this way**

- **Why a trigger and not package code.** Movements are inserted from the package, from SQL Workshop and (in real life) from imports. If only the package updated the stock, every other writer would get it wrong. A trigger runs for any insert, whoever writes it.
- **`AFTER INSERT ... FOR EACH ROW`** on `stock_movements` reads `:NEW.movement_type` and adds or subtracts `:NEW.quantity`. `:NEW` is the row being inserted.
- **Why `AFTER` and not `BEFORE`:** if a later check fails, an `AFTER` trigger's work is rolled back with the statement, and the movement is not recorded either. The rule stays consistent: no movement, no stock change.
- **The `CHECK` constraint is the last line of defence.** If someone inserts an OUT of 1 unit for an item with 0 in stock, the trigger's `UPDATE` would make the quantity -1, `ck_items_qty` refuses it with **ORA-02290**, and the whole `INSERT` is undone. The package gives the friendly error; the constraint is what makes it impossible to get it wrong.
- **`BEFORE INSERT OR UPDATE` on `items`** sets `:NEW.updated_at := SYSDATE`. Setting `:NEW` before the row is stored changes the value that is actually saved. This trigger also fires when the stock trigger updates the row, so `updated_at` moves whenever the stock changes.
- **No `WHEN OTHERS`:** a trigger that swallows errors records movements that never reached the stock. Let it fail.

**Oracle concepts:** row-level triggers, `BEFORE`/`AFTER`, `INSERT`/`UPDATE`, `:NEW` and `:OLD` (mentioned, not used here), `SYSDATE`, error propagation from triggers, constraint violation `ORA-02290`.

## 6. `plsql/03_views.sql`

**What it does:** two saved queries used by reports.

**Why it is written this way**

- A view is a stored `SELECT`. It holds no data; it runs the query each time. One definition means one place to fix when the rule changes.
- **`v_low_stock`**: `quantity_on_hand <= reorder_point` is the reorder rule, written once. The `LEFT JOIN` keeps items that have no supplier, and `NVL(s.supplier_name, 'No supplier')` prevents a blank column in the report. An inner join here would silently hide the newest item.
- **`v_po_summary`**: starts from `suppliers` with a `LEFT JOIN`, so a supplier with no orders still appears with 0. Joining PO headers to lines repeats a header once per line, so `COUNT(DISTINCT po.po_id)` counts the PO once, and `SUM(l.quantity * l.unit_price)` adds the money. `NVL(..., 0)` turns "no lines" into 0. `GROUP BY` lists every non-aggregated column.
- The view does not filter by status; a cancelled order still counts. That is a deliberate simplification, and it is a good thing to be able to discuss: filtering is the report's job, or a second view's job.

**Oracle concepts:** `CREATE OR REPLACE VIEW`, `INNER` vs `LEFT JOIN`, `NVL`, `SUM`, `COUNT`, `COUNT(DISTINCT ...)`, `GROUP BY`, aggregate over a one-to-many join.

## 7. `tests/test_inventory.sql`

**What it does:** eight anonymous blocks. Each one checks one behaviour and prints `PASS` or `FAIL`.

**Why it is written this way**

- **Anonymous blocks** (`DECLARE ... BEGIN ... END; /`) run once and are not stored. That is enough for a check script.
- **A nested block for the expected error.** When the test wants an exception (test 3, test 4b, test 6), the call sits in its own `BEGIN ... EXCEPTION ... END;` and sets a flag. The outer block then decides PASS or FAIL. This is the standard shape for "this should fail" tests.
- **`PRAGMA EXCEPTION_INIT`** turns an error number into a name: `-20002` becomes `e_cannot_receive`, `-2290` becomes `e_check_violation`. The tests catch those two codes and nothing else, so an unexpected error still fails loudly.
- **`ROLLBACK` at the end of every block** keeps the sample data unchanged, so the tests can be run again and again. Test 1, 7 and 8 only read data, so they need no rollback.
- **The expected quantity in test 4 is read from the PO line**, not hard-coded, so the test still makes sense if the quantity in the seed changes.
- `DBMS_OUTPUT.PUT_LINE` is how a PL/SQL block talks to you. In SQL Workshop the output appears automatically; in SQL*Plus you need `SET SERVEROUTPUT ON`.

**Oracle concepts:** anonymous blocks, nested blocks, exception handling by name, `SQLCODE`/error numbers, `NVL` and `TO_CHAR` for messages, `TRUNC` on dates, `ROLLBACK` in tests.

## 8. How the pieces work together

What happens when you call `inventory_pkg.receive_po(3)`:

1. The PO row is locked and must be `ORDERED`.
2. One `INSERT ... SELECT` writes one IN movement per PO line (item 11 × 120, item 12 × 40).
3. For each inserted movement, `trg_movements_ai` adds the quantity to `items.quantity_on_hand`.
4. That `UPDATE` fires `trg_items_biu`, which sets `updated_at` to now.
5. `SQL%ROWCOUNT` confirms lines were written, and the PO is set to `RECEIVED`.
6. Nothing is committed: the caller commits, or rolls back everything above.

The same chain protects the other direction: `issue_stock` checks the stock, inserts an OUT movement, the trigger subtracts, and the `CHECK` constraint refuses anything that would go negative.

## 9. Ways to describe this project in an interview

Short, honest sentences that match the code:

- "I built a small inventory schema in Oracle 19c with five tables and referential integrity enforced by foreign keys."
- "Stock is derived from movements: a trigger on `stock_movements` keeps `items.quantity_on_hand` in sync, and a `CHECK` constraint makes negative stock impossible."
- "I put the operations in a package so the public API is separate from the implementation, and the package raises a named exception bound to ORA-20001 for insufficient stock."
- "The package never commits; the caller controls the transaction."
- "I wrote eight small tests as anonymous PL/SQL blocks that print PASS/FAIL and roll back, so they are safe to re-run."
